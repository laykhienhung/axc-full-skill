# ProtoFlow — prototype UI: the customer view

The prototype is shown to the **customer**, who should feel they are using the real product. It is not a spec viewer. Every screen must look and behave like a page of a live website. Traceability stays fully intact, but it lives in a **review layer** the BA switches on, not on the page.

`/protoflow-prototype` follows this guide for every screen it generates.

## Two layers

| Layer | Who | What it shows | How |
|-------|-----|---------------|-----|
| **Customer view** (default) | the customer | the product: brand, navigation, real pages, realistic data, plain-language messages | what every screen renders |
| **Review layer** | the BA, in the meeting | the screen list, open questions, assumptions, conflicts, simulated parts, element ids, persona switcher, reset data | the ⋯ tab (bottom-right) or the `` ` `` key → "review mode" / "show ids" |

The review layer is **added on top of** the customer view. It never replaces it.

## Never visible in the customer view

- Spec ids or spec words: `SCR-`, `REQ-`, `BR-`, `FLOW-`, `UC-`, `ENT-`, "screen", "flow", "entity", "requirement", "prototype", "seed".
- Raw data: enum codes (`IN_PROGRESS`, `MID`), JSON, field/column names (`overall_outcome`), `null`, `undefined`, `NaN`, `[object Object]`, ISO timestamps with a `T`.
- A screen's `Purpose:` line used as a subtitle. Write the product's own copy instead.
- "Open question", "Assumed", "Conflict", "Simulated", or "not specced" text in the page body. Those go through `ctx.note()`.
- Stack traces or SQL errors. Show a friendly message, and put the detail in `ctx.note("Error", …)`.
- Dead ends: a link or button that does nothing, a blank page, a 404.

## Where traceability goes

- **`data-ref`** on the page heading (`SCR-`), on each action (`REQ-` / `FLOW-`) and on each rule message (`BR-`). These are invisible until "show ids" is on.
- **Review notes**: every item typed `ASSUMPTION`, `UNKNOWN` or `CONFLICT` that concerns a screen is rendered under it automatically (`notes.js`, generated by the compile script). Screens call **`ctx.note(kind, text, ref)`** only for simulated parts or to say what the page does meanwhile. It renders a review-only note (hidden in the customer view) and keeps the id in `ref`.
- **`ctx.violate(BR, message)`** for a broken business rule. The **message is customer guidance** ("That time slot is already booked — pick another one."). The rule id travels only in `data-ref`.
- The **screen list** (left sidebar) appears only in review mode.

## App chrome: `prototype/app.js`

Every customer-facing screen starts with the same product chrome, generated once per run into `prototype/app.js` (see `templates/prototype/app.example.js`):

- **Brand:** the product name, taken in this order: a `DECISION` naming the product; the grounding; else the humanized project id. Use a simple wordmark, and never write "prototype".
- **Primary navigation:** the confirmed Feature-scope items a customer would see, in Feature-scope order, labelled in the customer's words.
  - A feature that is specced links to its entry screen.
  - A feature that is confirmed but not specced yet **stays in the nav**, because the real product will have it. Clicking it shows a "coming soon" toast. It is never a dead link.
  - Staff and back-office features don't go in the public nav.
- **Account area:** "Sign in" for a guest; the person's name or "Account" for a signed-in user.
- **Language switch:** only when a requirement asks for more than one language. Every customer-facing string then goes through `t()`.
- **Persona switcher:** "View as" sits in the review panel (`#devExtra`), never in the product nav. It lists one seeded user per actor or role in the use cases, plus "Guest" when the product has public pages. Screens read the current persona and behave like the real app: a signed-in-only page sends a guest to the landing or sign-in screen.
- **Back-office screens** (admin, reviewer, staff) use the back-office chrome variant: a sidebar or tabs, with dense tables.

## Pick a page type for every screen

Decide from the screen's Purpose, Fields, Actions and actor. Every screen gets exactly one type.

| Page type | Use when | Must have |
|-----------|----------|-----------|
| **Landing** | a public entry point, first impression | hero headline + subline, value points, primary calls to action as large cards or buttons |
| **Dashboard / home** | a signed-in start page | greeting, a priority banner for the one thing to do now (resume, pending approval), stat tiles, cards to next actions, an inviting empty state |
| **List** | browsing many records | page title + primary action button, filters/search when there are more than about 8 rows, table or card list, status badges with human labels, a row click opens the detail, an empty state with a call to action |
| **Detail** | one record | title + status badge + actions at the top right, sections in panels, related records |
| **Form / wizard** | creating or editing | one narrow column, labels in plain words, helper text, inline validation, primary + secondary buttons. Split into steps with a progress indicator when there are more than about 6 fields |
| **Conversation** | chat, interview, messaging, support | message bubbles (theirs left, mine right), a composer pinned at the bottom, a "thinking…" state, auto-scroll to the latest message |
| **Decision dialog** | a choice with consequences | a centered panel that states what each option will do, primary + outline buttons, and Cancel |
| **Result / completion** | the end of a flow | a clear outcome heading, a short summary, the next step as a call to action |
| **Back-office** | staff tools (review queues, configuration) | the back-office chrome, dense tables, bulk actions, status filters |

## Copy and formatting

- Use the customer's vocabulary from the glossary, in sentence case.
- Buttons state the action and its object: "Send answer", "Approve booking". Not "Submit" or "OK".
- Format values for people:
  - dates as "2 Oct 2026", or relative ("yesterday");
  - money with its currency;
  - enum values mapped to labels (`IN_PROGRESS` → "In progress"), shown as a colored badge where it is a status.
- Messages say what happened and what to do next. Success messages are short and confirm the outcome.
- Greet people by their given name.
- Empty states invite action: "No bookings yet — book your first room." Never just "No data."

## States

Render each state the screen lists, as the real app would:

- **loading**: skeletons or a spinner;
- **empty**: an invitation with a call to action;
- **submitting**: the primary button disabled with a progress label;
- **error**: a friendly message with the detail in `ctx.note`;
- **success**: a toast, plus the page reflecting the change.

## Realistic data and fake services

- **Seed data makes every screen look lived-in:**
  - fictional but plausible names in the customer's locale;
  - dates near today;
  - 5–8 rows for lists;
  - one persona per state the screens list (new user, active user, user with a pending item, staff).
- **External systems are simulated in-app** (AI, payment, email, SMS, maps). Simulate realistic latency (0.5–1 s) with a "thinking"/"processing" state, and return plausible output. Mark the fake with `ctx.note("Simulated", …)`, never in visible text.

## Visual baseline

- Build with the **`ui.js` kit** (page head, cards, tables, forms, filters, gallery, overlays, skeletons, empty/result states…) — `app.css` already styles all of it. Hand-written markup only for what the kit lacks.
- Theme with the token block at the top of the engagement's `app.css` (`--brand`, `--brand-soft`, `--radius`, `--display`, `--max`). Product-specific CSS goes in one short "product touches" block, never per screen.
- Keep a centered content width, generous spacing, and one primary button per view.
- Layouts must work at 375px wide (grids collapse, nothing scrolls sideways) unless a `DECISION` makes the prototype desktop-only.

## Done checklist (verify in a browser)

Before reporting, open the prototype with `python serve.py`. Run `window.protoSelftest()` (screen samples + scripted `WALKS`) at each supported width; it covers most of this list:

1. Nothing from "Never visible in the customer view" appears, including in toasts.
2. Every link and button does something real, or shows "coming soon".
3. Each persona sees what the real product would show them, and gated pages redirect.
4. Each listed state can be reached, and each `BR-` can be triggered and shows customer guidance.
5. Review mode shows the screen list and every `ASSUMPTION` / `UNKNOWN` / `CONFLICT` note; "show ids" tags the heading, the actions and the rule messages.
6. A deep link or refresh on a screen URL loads correctly, and "reset data" works on any screen.
